# 发微信朋友圈（Windows 桌面）

驱动微信 PC 客户端 UI 发图文朋友圈。已在本机验证可用。

## 何时使用

用户说「发朋友圈」「发一条朋友圈」「把这个发朋友圈」「帮我发个圈」。需要**图片**（微信朋友圈必须配图）。

## 前置检查

微信必须已登录。先确认窗口存在：

```powershell
powershell -NoProfile -Command "Get-Process Weixin -ErrorAction SilentlyContinue | Select-Object -First 1 Id"
```

没有进程则提示用户先打开微信。

## 执行

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "%USERPROFILE%\.dsh\skills\wechat-moments-post\wechat-moments-post.ps1" -Image "C:\absolute\path\pic.jpg" -Text "配文内容"
```

参数：

| 参数 | 必填 | 说明 |
|------|------|------|
| `-Image` | 是 | 图片绝对路径，支持 jpg/png |
| `-Text` | 否 | 朋友圈配文，可中文 |
| `-DryRun` | 否 | 只打印探测到的窗口坐标，不动桌面 |
| `-Quiet` | 否 | 静默 |

**先 `-DryRun` 验证窗口探测**，再实际执行。

## 配文风格

用户没指定文案时，写一句自然的、符合图片内容的中文短句，不要写「分享一张图片」这类说明式废话。控制在 30 字内。

## 脚本内部流程

1. 找微信主窗口（`微信` / class `Qt51514QWindowIcon`）
2. 点左侧「发现」→「朋友圈」
3. 点右上角相机图标 → 文件选择框
4. 文件名框填图片路径 → 回车
5. 发布框填文案
6. 找绿色「发表」按钮（按像素颜色定位）→ 点击

## 已知的坑（脚本已处理，出问题时对照）

| 现象 | 原因 | 处理 |
|------|------|------|
| 找不到「朋友圈」窗口 | 微信有时内嵌渲染在主窗口，不产生独立窗口 | 脚本已兼容两种模式 |
| 相机点一次文件框不弹 | 内嵌模式下弹出慢 | 脚本轮询 12 秒，不弹再点一次（实测第 2 次才弹） |
| 朋友圈区域截图是黑块 | 微信硬件加速窗口抓屏限制 | 用整屏截图判断，别用区域截图 |
| 标题栏三个图标点错 | 刷新/铃铛/相机挨得很近，间距约 22~30px | **相机在最右**，中心在 `右边界 - 44px`、`顶部 + 55px`。用 `-46` 会点到**铃铛**，弹出「全部互动消息」面板 |
| 反复滚 30 轮反而滚乱 | 滚动消息被窗口丢弃、滚动过头 | 只滚一轮（12 下），靠相机重试兜底 |
| 脚本中文乱码/解析报错 | PowerShell 5.1 按 GBK 读脚本 | 脚本必须是 UTF-8 **带 BOM** |

## 失败处理

脚本抛错时**不要盲目重试**（朋友圈已发出会重复）。先看错误：

- `微信主窗口没有打开` → 让用户开微信
- `没能进入朋友圈` → 手动把微信切到朋友圈页面，再跑脚本
- `文件选择框没有出现` → 相机按钮位置可能因窗口大小变化偏移，用 `-DryRun` 核对坐标
- `发布框没有出现` → 图片可能没选中，**先手动确认朋友圈有没有意外发出**

## 验证

脚本成功会打印 `Stage : published` 和点击坐标。发布后建议截图确认信息流顶部出现新动态。

**不要用数据库验证**：sns.db 被微信进程锁着，直连会报 `file is not a database`。

# 附：回复朋友圈评论

同目录的 `wechat-moments-reply.ps1` 用来**回复自己动态下的评论**。已在本机真机验证。

## 何时使用

用户说「回一下评论」「回复朋友圈评论」「自动回评论」、或问某条评论该回什么。

## 先列出待回复的评论

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "%USERPROFILE%\.dsh\skills\wechat-moments-post\wechat-moments-reply.ps1" -List
```

`-List` 会读 reader API（`127.0.0.1:5031` 的 `/api/v1/sns/mine`，必要时先 `/api/v1/sns/comments` 补齐），
列出自己动态下的评论，并标注哪些已经回过（本地账本 `<workspace>\state\moments-replies.json`）。
**Reader 没起时先让 WeChatAgent 把 reader 拉起来**，否则拿不到评论。

## 执行回复

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "%USERPROFILE%\.dsh\skills\wechat-moments-post\wechat-moments-reply.ps1" -ObjectId <动态id> -CommentId <评论id> -Text "回复内容" -Execute
```

| 参数 | 说明 |
|------|------|
| `-List` | 只列出待回复评论，不动桌面 |
| `-ObjectId` | 动态 id（`-List` 里能看到） |
| `-CommentId` | 评论 id |
| `-Text` | 回复内容 |
| `-Execute` | 真正执行 UI 回复；不加只做演练 |

## 脚本怎么定位（不依赖模型看图）

全流程用 Windows 自带 OCR（`Windows.Media.Ocr`，zh-Hans-CN），图像放大 2 倍识别。

**不要往信息流里翻。** 自己发的旧动态在全局信息流里早就沉下去了，滚几十屏也找不到。
正确路线是走「我的朋友圈相册」，那里只有自己的动态：

1. 点**左侧栏最上面的头像**（固定位置，窗口左上角偏下）→ 弹出个人资料卡
2. 点资料卡里「朋友圈」标签右侧的缩略图 → 打开「我的朋友圈」相册（占窗口右半边）
3. 在相册里按动态正文前 14 字找目标动态（先看当前屏，找不到再往下滚，最多 12 次）
   - 正文短于 4 字的动态（如「微信小视频」）**直接报错退出**，不去盲滚——匹配不可靠
4. **点它的正文**打开「详情」页
5. 在详情页里按**界面显示名**定位评论作者行（显示名从 reader `/api/v1/contacts` 查，见下）
6. **点「时间戳左边那道空白」**——固定在时间戳左端往左约 34px：
   - 点昵称 → 弹个人资料卡，错
   - 点时间 → 没反应，错
   - 点时间戳左边一点 → 底部立刻弹出「回复 XX」输入框 ✅
7. **核对占位字**：回复框里写的是 `回复 <谁>`，必须和目标显示名对得上，对不上就退出不发
8. 点进输入框，粘贴回复文字
9. 点绿色「发送」按钮（文字进去后按钮才变绿，可按颜色扫描定位）
10. 发送后 OCR 确认评论区出现了「回复 X：刚发的话」，再写本地账本

### 显示名：解决「回复错人」的关键

DB 里的 `nickname` 是原始昵称，界面上印的是**备注名**（`真由理`→`南华`、`翮`→`高一健身李帅佐`）。
按原始昵称去 OCR 里找，永远找不到，只能退化到按正文模糊匹配，短评论就会串到隔壁那条、回复到别人头上。

脚本启动时对每条待回复评论查一次 `GET /api/v1/contacts?keyword=<wxid>&limit=5`，取 `displayName`：

```powershell
$hdr = @{ Authorization = "Bearer $TOKEN" }
$ct  = Invoke-RestMethod "$READER/api/v1/contacts?keyword=$q&limit=5" -Headers $hdr -TimeoutSec 15
$dn  = (@($ct.contacts) | Where-Object { $_.username -eq $username } | Select-Object -First 1).displayName
```

拿到显示名后，在详情页里直接找那一行，**相似度 ≥ 0.80 才认**，比正文模糊匹配精确得多，
3 个字的「可爱捏」这种也能一次点准。

### 为什么按正文、按时间戳定位，而不是按昵称 / 按名字宽度

- **昵称不可靠**：DB 里存原始昵称，界面显示的可能是有备注名的那个（`真由理` 在界面上叫 `南华`）。
  解法是用 reader 查显示名，见上一节。
- **名字宽度不可靠**：名字长短不一，按「名字右端到时间戳的中点」算，长名字会把点击点推到名字上。
  时间戳位置是固定的，直接钉死在时间戳左边一点最稳。

### 截图裁剪与坐标换算（改动这里容易点偏）

相册和详情页都只占窗口右半边，所以 OCR 截图裁成 `x 从 50% 到 100%`，文字量少一半，
也不会把左边信息流里别人的动态误认成自己的。

**裁了就必须跟着换算**：OCR 出来的 `X` 是相对那张裁剪图的，不是相对窗口。
`Ocr-Window` 会给每一行挂上 `OX`/`OY`（该截图的原点），所有「OCR 坐标 → 屏幕坐标」
一律走 `$ln.OX + $ln.X`，**不要再写 `$wr.Left + $ln.X`**。

踩过的坑：`$row` 是包装对象不是 OCR 行，写 `$row.OY` 得到 `$null`，
Y 就少了窗口偏移 40px，整行点偏到上一条评论上（回复框弹出「回复 南华」而不是目标）。
取原点要从真正的行上取：`$nickLine.OY` / `$dateLine.OY` / `$row.Body.OY`。

### OCR 的注意事项

- OCR 会把中文拆成单字（`就 吃 白 饭`），比对前必须去掉所有空白。
- 小字号昵称常整行读不出来（返回 `0` 或空），所以不能依赖昵称。
- 楼中楼整行是「回复 <某人>：<正文>」，正文被包在里面；要把**原始文本按冒号切开**取后半段再比对
  （`Normalize` 会把冒号删掉，所以只能在原始文本上切）。
- OCR 也会认错字（`有意思` → `有琶思`），所以用小阈值 + 取最相似行，而不是精确匹配。

DB 里的 nickname 是原始昵称，界面上可能显示备注名（例如 `tuet` → `关胜伟`）。

### 回复框长什么样

底部出现一个浅色圆角框，占位字是 `回复 <昵称>`，下面一排图标（语音 / 表情 / 图片），右下角是绿色「发送」。
没输入内容时「发送」是灰的，有文字后变绿。

判据：底部有一条**以「回复」开头、且不带冒号**的行（评论区里的「回复 X：…」都带冒号）。

## 已知的坑（脚本已处理）

| 现象 | 原因 | 处理 |
|------|------|------|
| 点评论毫无反应 | 点到正文或时间戳了 | 只能点昵称右侧、时间左侧的空白 |
| 点评论弹出个人资料卡 | 点到昵称本身了 | 往右偏到空白处 |
| 「回复 XX：」读不到 | 它是浅灰占位字 | 判定改用「粘贴后的文字能否 OCR 到」，短文本阈值放宽到 0.55 |
| 找不到「发送」按钮 | 白字绿底，OCR 失败 | 按颜色扫描绿块 |
| 坐标漂移 | 朋友圈平滑滚动 | 每次重试都重新截图重新定位；滚完等 1.5 秒 |
| 脚本中文乱码 | PS 5.1 按 GBK 读 | 必须 UTF-8 **带 BOM** |
| **按 Esc 会把微信搞崩** | 详情页里 Esc 连带关掉父窗口 | 脚本里**永远不要发 Esc**；关浮层只点别处 |

## 安全约定

- 发送前必须确认回复对象；宁可不发，也不要发给错的人
- **占位字硬校验**：回复框弹出后，占位字 `回复 <谁>` 必须和目标**显示名**相似度 ≥ 0.50，否则 `exit 2`，一个字都不发。
  这条取代了早先「只有短评论才校验」的宽松规则——因为现在显示名查得准，可以一直校验。
  实测拦下过一次：本来要回「贤真的不闲」，回复框却写着「南华」，说明点到了上一条评论。
- **跳过自己**：脚本按配置里的 `ownWxid` / `ownNick` 跳过本账号的评论，不回复自己
- 已经发出去的不会撤回：脚本在发送前失败会 throw，不会重试发送
- 账本记录 `对象:评论id`，同一评论不会回第二次
- **发完不按 Esc**：详情页里 Esc 收不掉回复框，且曾把微信搞成白屏重启。回复框留着不影响下一条——
  脚本每轮都从相册重新进来，坐标实时算。


## 回复框检测：三个必须知道的坑（2026-10-27 实测）

1. **检测回复框时截图绝对不能抢焦点。**
   `Capture-Window` 默认会 `ShowWindow + SetForegroundWindow` 把主窗口提到最前，
   而回复框是依附在主窗口上的浮层 —— 一提主窗口，回复框就被压下去，
   于是截图永远拍不到、判定成「没弹出」，然后重试点击，越重试越拍不到。
   已加 `-NoActivate` 开关：`Test-ReplyBox`、输入后校验、发送后校验三处都必须带上。

2. **（已被下方「最终方案」取代）占位字 OCR 会丢字。** 「回复 源」实测被读成 `回源` / `回过源`。
   所以判据不能写 `StartsWith('回复')`，改成「以 `回` 开头且整行 ≤24 字」；
   剥前缀时「回复」「回」都要剥。
   校验点错人时，除了相似度，再加一条：**整行包含目标显示名就算命中**。

3. **冒号要判原文，不能判 Normalize 后的文本。**
   `Normalize` 会把 `：` `:` 全剥掉，评论区里的 `回复 X：内容` 会被误当成占位字。
   必须用 `$ln.Text.Contains('：')` 在归一化之前判断。

## 点击落点

评论作者行只有十几像素高，`+7` 的偏移会把它推到行下沿之外。
现在用 `$rowOY + $rowY + 2`（行内偏上），失败重试再纵向 ±6 / ±12 扫一遍，
最后才横向往右挪（`nameRight + 40`、`0.88 * winW`）。

## 窗口尺寸会漂

微信主窗口在 `803x1025`（只有信息流）和 `1204x1537`（右侧开了相册/详情）之间切换。
所有坐标必须每次用 `GetWindowRect` 现算，不能缓存。
## 回复框检测：最终方案（2026-10-27 二次修正）

### UIA 这条路走不通（已实测，不要再试）
- 回复框**不是独立窗口**，是画在主窗口里的浮层，UIA 树里没有对应控件。
- 那个 class `Qt51514QWindowToolSaveBits` 的窗口实测 `descendants = 0`，而且只有 66x98，
  是输入法/提示类小窗，不是回复框。
- 主窗口 `Qt51514QWindowIcon` 的 UIA 树里正文/评论/回复框全都不出现（Chromium 内核）。

### 占位字不能按文字内容判断
实测同一句「回复 源」被 OCR 读成过：`回源`、`回过源`、`丨回原kagami`、`回复 源`……
任何 `StartsWith('回复')` / `StartsWith('回')` 的判据都会漏判。
**漏判的代价特别大**：判定成「没弹出」就会重试点击，而重试点击会把已经打开的框点没了，
于是越重试越检测不到。

最终判据 —— **只看位置和形状，不看内容**：
```powershell
# 底部（Y ≥ 0.60 * 高）最靠下、且满足：
#   1. 不是「发送」
#   2. 原文不含冒号（评论区「回复 X：内容」都带冒号）
#   3. Normalize 后长度 ≤ 24
```
取 Y 最大的那一行作为占位字。

### 占位字读烂时怎么办
`$row.By -eq 'name'`（按显示名精确定位，相似度 ≥0.80 才认）时，
占位字相似度低**只警告、继续发** —— 因为点击落点本来就是按名字精确匹配的。
`$row.By -eq 'content'`（按正文兜底）时仍然硬拦，那条路本来就可能点到隔壁。

### 输入区与发送
- 输入区：点占位字那行的中心（`Line-Center`）。
- 发送按钮：优先 OCR 找「发送」，找不到就按 `#07C160` 绿色扫描（空框时按钮是灰的，扫描不到，
  但输入文字后会变绿）。
- 发送后校验：再 OCR 一次，评论区出现「回复 X：<刚发的话>」才算成功。
## 发帖：相机点不中的根因（2026-10-27 实测）

`wechat-moments-post.ps1` 的相机坐标是 `Right - 44, Top + 55`。
内嵌模式下没有标题为「朋友圈」的独立窗口，`Find-Win -Title '朋友圈'` 一直返回空，
于是 `$moments` 停留在脚本开头读到的**旧尺寸**上。

实测窗口宽度会在 `439 / 658 / 803 / 1204` 之间来回变（开相册/详情页会变宽，关掉又变窄）。
一旦变窄，按旧尺寸算出的 `camX` 就落到窗口外，点 4 次相机全落空 → 抛「文件选择框没有出现」。

修法：
1. 每次重试都重新读几何 —— `Find-Win '朋友圈'` 找不到就回退 `Find-Win '微信'`。
2. 相机偏移做档位兜底：`44 / 36 / 52 / 44`，每个重试换一档。

另外「发表」按钮偶尔 OCR 认不出，日志会打 `[warn] 绿色按钮未确认` 并按几何位置点。
实测这种情况也能发出去，但属于软校验，发布后要用 reader `/api/v1/sns/mine` 复核。
